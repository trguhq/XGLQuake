## Development-host checks

Shareware recognition, CPU texture/mesh, native UI/entity/particle submission, audio
queueing and profiling tests need no SDK or game data. They run against
controlled engine/backend mocks. Alias color checks also use the real CPU
texture sampler to compare cached output with the original color calculation.
The SMP tests use a real POSIX worker with controlled CPU counts and startup
failures to check mode selection, queuing, reclaiming of unstarted jobs,
draining, and shutdown. The world and entity tests also cover drawing order
by native state, map-load mesh building, the per-frame build limit, detail
eviction and the identity record that lets model caches skip comparisons;
detail placed by contrast and by apparent size; and geometry submitted with
and without normals, including the copies walls keep for dynamic lights.
The entity tests also draw a model as triangle strips and as separate
triangles and require the same triangles either way, from the serial path
and from the worker's output, and the mesh tests check the loader's record
of which vertices are one point.
The shape tests examine made-up textures: which have shapes and which do
not, bands, sloping edges, where a repeat begins, and the frames of an
animated texture. They cut faces along the result and check that the pieces
cover the face exactly, have the texture's colors, and share every corner
that lies along a side. The world tests then draw such walls: their colors
and baked light, the steps of detail by distance, and the limits.
The screen tests cover when an unchanged status bar is left in place, and
the UI tests that every picture name draws what it did before.
Run from `WinQuake/`:

```sh
make -f Makefile.XGL check
```

These tests require a modern host compiler and GNU-compatible linker. They
are separate from the native Solaris build. For complete engine compilation
and a host link with native API placeholders, run:

```sh
make -f Makefile.XGL host-check XGLHOME=/path/to/xgl-sdk
make -f Makefile.XGL native-contract-check XGLHOME=/path/to/xgl-sdk
```

The `host-check` target requires Python 3, a modern host C compiler, and the
actual Sun XGL SDK headers supplied separately. Host-only handwritten X11
and Solaris contracts provide declarations needed where native development
headers are unavailable. They are not substitutes for native libraries.
To use real X11 development headers instead, add
`HOST_X11_INCLUDE=/path/to/include` to the host-check command.
The executable generated by `host-check` is linked only, never executed; native API
placeholders abort if called. This catches unresolved engine symbols and
accidental OpenGL dependencies. The check also compares modified existing
shared engine files against `HEAD` under software and `GLQUAKE` preprocessing to
verify that their existing paths remain unchanged. Temporary artifacts and
the compiler log are reported by the script.

The `native-contract-check` target builds and runs mocked backend tests
against the SDK headers; it does not require Python. It captures SDK calls to check projection,
clipping, lighting selection/state changes and their count, gamma and
native font placement/cache behavior, including spaces kept inside text
runs. It also checks view placement after
resizing, strided/prepared vertex colors, cached/direct geometry batches of
points with and without normals, a clear that leaves the status bar's rows
alone and the mapping restored after it, queued UI text and rectangles and
their order and lifetimes, completion waits, and error diagnostics
with missing library message fields.
It does not rasterize those calls.

These host checks do not establish Solaris linking, SPARC ABI compatibility,
native font rendering, Sun ZX correctness, or performance. Validate changes
with a native build and game run on the target Sun, including map startup,
gameplay, audio, fonts, lighting, and transparency. No game assets are bundled
with the host checks, and host test results do not establish hardware FPS.

## Compare single-CPU and SMP rendering on the Sun ZX

On the dual-processor machine, run the same executable from the directory
containing `id1/`. Use the same display, demo, game data, and detail settings
for both runs. The 320×240 window matches the supplied `demo1` profile.
On Solaris, `psrinfo` lists the processors and their online state.

```sh
./xglquake -winsize 320 240 +_snd_mixahead 0.3 +xgl_smp 0 +xgl_profile 0 +timedemo demo1 > demo1-serial.log 2>&1
./xglquake -winsize 320 240 +_snd_mixahead 0.3 +xgl_smp 1 +xgl_profile 0 +timedemo demo1 > demo1-smp.log 2>&1
```

Keep the console closed during playback and quit after each result appears.
The last `XGL SMP:` status line in each run gives the requested mode,
online CPU count, and whether the worker started. Repeat each mode and
compare median elapsed time for the same frame count. At 15 FPS the frame
budget is 66.7 ms. Compare the same demo scenes for model pose, sampled
colors, lighting, and drawing order.

The game saves `xgl_smp` in `config.cfg`. To restore automatic selection
after testing, enter `xgl_smp -1` at the game console. Check this on both
machines. With both CPUs online, the dual-SM61 should report one worker.
The single-SM61 should report single-threaded rendering.

To locate a timing difference, repeat both commands with `+xgl_profile 2`
and separate log filenames. Use the unprofiled runs for the FPS comparison.
The profiled single-CPU run of 19 November 2026, made before the changes
that [Measured on the Sun ZX](hardware.md) led to, recorded 969 frames in
77.3 seconds (12.5 FPS). Dual-SM61 speedup and the 15 FPS target still
require hardware measurements.
